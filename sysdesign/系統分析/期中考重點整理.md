## 1. 第一章：資訊系統開發概論

### 1-1 什麼是「資訊系統開發」

> **一句話**：用**資訊科技**＋**開發方法**，把公司要的東西做成電腦系統，解決「資料處理」的需求。

**開發原則（7 條，老師列點）**
1. 系統的目標應該**明確定義**
2. 系統的目標要**實際而有用**
3. 系統開發要**充分運用科技**
4. 系統開發要**依循一定的方法**
5. 系統開發必須獲得**足夠的資源與支持**
6. 系統開發必須**符合限制條件**
7. 系統開發必須**考慮環境因素**

### 1-2 開發過程：三階段 vs 七階段（會考配合題）

| 三階段（簡單系統） | 七階段（複雜系統） |
|---|---|
| 需求分析 → 系統分析與設計 → 系統實施 | 使用者需求分析 → 軟硬體需求分析 → 系統分析 → 系統設計 → 編碼 → 測試 → 操作與維護 |

> **記法**：三階段是「大方向」，七階段是「拆細」。系統越大，切越細。

### 1-3 開發構面（4 個）

| 構面 | 一句話 |
|---|---|
| **人** | 開發極度依賴人；有經驗的人＝高生產力，「成也在人、敗也在人」 |
| **方法** | 開發模式＋分析設計技術，一套合乎邏輯且驗證過的流程、步驟、技術 |
| **科技** | 資訊系統是資訊科技的產物；科技的研發、選擇、管理決定成敗 |
| **企業經營** | 系統目的在支援企業經營，把企業需求轉換成系統 |

### 1-4 開發特性（3 個）與挑戰（4 個）

**特性**
1. 軟體是**人造的邏輯系統**（設計者必須完全了解程式邏輯）
2. 軟體開發是**專業工作**（門檻高、養成時間長）
3. 軟體開發是**智力活動**（潛能無窮、個別差異大，也充滿錯誤與偏誤）

**挑戰**
1. 科技進步快、淘汰率高 → 系統可用壽命變短
2. 經營環境變遷快 → **使用者需求經常變動**
3. 時程延誤、成本超支、品質不良普遍存在
4. 智慧財產權重視不足 → 軟體價值被低估、開發成本被低估

### 1-5 ⭐ 系統觀念圖（**每年都愛考，一定要會畫**）

```
                ┌──────────── 外在環境 (Environment) ────────────┐
                │  供應商 Suppliers   顧客 Customers              │
                │  競爭者 Competitors 銀行 Bank                   │
                │  政府 Government    天災/天氣 Weather           │
                │ ┌────────── 系統邊界 System Boundary ────────┐ │
   Input ───────► │  ┌──────────┐   ┌────────────┐   ┌────────┐ │ ──────► Output
（進入系統的元素）│  │  Input   │──►│ Processing │──►│ Output │ │（完成品）
                │  └──────────┘   └────────────┘   └────────┘ │
                │        ▲               ▲              ▲      │
                │        └───── Controller ─────────────┘      │
                │            （虛線＝Feedback signals 回饋訊號） │
                └──────────────────────────────────────────────┘
```

**核心 4 元素**：Input（輸入）、Processing（處理）、Output（輸出）、**Controller（控制者）**

**Controller 為什麼存在？**
- 因為有 **GIGO（Garbage In, Garbage Out）垃圾進、垃圾出**。
- 老師的例子：老師分數打錯 → 成績單錯 → 平均也錯。所以必須監控**輸入資料**是否正確。

**實線 vs 虛線（考過）**
| 線 | 意義 | 例子 |
|---|---|---|
| **實線**（有箭頭） | 真正有**東西**流到下一個地方 | 原物料、資料 data |
| **虛線** | **虛擬的訊號**，不是實體資料、不會被記錄 | 監控發現錯誤時**彈出的對話方塊／警告訊息**（只顯示在螢幕上） |

**IPO 例子對照表（老師用同一張圖套三個例子，很愛問）**

| 系統 | Input | Processing | Output |
|---|---|---|---|
| 化學工廠 | 未加工原物料 | 製造生產 | 產品 |
| 電腦化資訊系統 | **Data（資料）** | **程式產生作用（執行）** | **Information（資訊）** |
| 醫院 | 病人 | 醫生看診 | 痊癒的病人 |

> **記憶點**：資訊系統＝把 **Data 變成 Information** 的過程。

### 1-7 ⭐⭐ 資訊系統的種類（**本章最核心，必考**）

```
資訊系統
├─ 作業支援（中低階層在用）
│   ├─ TPS　交易處理系統
│   ├─ 流程控制系統
│   └─ 企業間合作系統
├─ 管理支援（中高階層在用）
│   ├─ MIS　管理資訊系統
│   ├─ DSS　決策支援系統
│   └─ EIS　高階主管資訊系統
└─ 其他：ES 專家系統、SIS 策略資訊系統、KMS 知識管理系統、
         ERP 企業資源規劃、整合型資訊系統、企業資訊系統…
```

#### (1) TPS 交易處理系統（Transaction Processing System）

- **定義**：利用電腦處理公司**日常例行性**的交易資料，是公司**最基本**的系統；主要目的在**將大量交易處理自動化**。
- **兩大功能**：① **交易記錄之保存**　② **交易表單（畫面）之產生**
- **特色**：資料**最完整**（每天每筆都記錄）→ 後續大數據、Data Mining、統計圖表都從這裡挖資料。
- **例子**：POS 系統**前檯**、加油站加油作業、收銀系統、金融機構櫃檯系統。
- **兩種處理方式（常考）**：

| 方式 | 定義 | 例子 |
|---|---|---|
| **批次處理 Batch** | 交易發生時**不馬上處理**，累積一定量再一起做 | **薪資計算**（每天記錄出勤，月底 30/31 天才算薪水） |
| **即時處理 Real time** | 交易發生時**馬上處理** | 便利商店結帳、銀行抽號碼牌臨櫃 |

#### (2) 流程控制系統

- 控制**實際作業流程**的系統。
- 例子：**自動檢測存貨量**是否低於安全庫存量 → 不足就自動提醒進入採購流程；石油精煉用電子感應器連電腦持續監控石化過程；生產線某一關卡的電腦監控。
- 寫程式做法：設兩個欄位「**安全庫存量**」與「**實際庫存量**」，實際 < 安全 → 畫面自動彈出提醒採購。

#### (3) 企業間合作系統

- 用資訊科技讓**很多（跨公司）人員一起工作**，促進溝通、協調、資源分享（如視訊會議）。
- 目標：提高團隊**生產力**與**創造力**。

#### (4) ⭐ MIS 管理資訊系統（**最常考解釋名詞**）

- **定義（背 Davis 1968 的版本，分數最高）**：
  > 「管理資訊系統是一種**人機整合系統**，它提供**資訊**以**支援組織的日常作業、管理以及決策活動**。這一類系統使用到電腦硬體、電腦軟體、作業程序、企業問題模式及資料庫等科技。」
  > —— Davis（1968）
- **為什麼要寫 Davis？** MIS 有很多學者定義，寫權威學者的定義分數較高（Davis 是資管領域權威）。
- **四個組成**：**人、機、資訊、組織**
  - 人：資料提供者、資料處理者、資訊使用者、決策者
  - 機：硬體、軟體、通訊
  - 資訊：原始資料＋處理過的資訊
  - 組織：在競爭環境中靈活運用資源以達企業目標
- **用到的資訊科技**：電腦硬體、作業系統（軟體）、**作業程序**（功能之間有先後順序，A 做完才能做 B）、**資料庫**（任何資訊系統都需要）。
- **POS 系統的「後檯」屬於 MIS**（前檯屬於 TPS）← 這個對照很愛考！

#### (5) DSS 決策支援系統（Decision Support System）

- **定義**：強調**協助人們做決策**的電腦應用系統；偏向用來**規劃、分析行動方案**，以**試誤法（Try and Error）**找答案，以**交談方式**解決**半結構性問題**，強調的是**支援**。
- **Try and Error 循環**：找方法 → 試 → 不行 → 再找第二個方法 → 再試…（一直循環，直到找到最好的決策）。
- ⭐ **問題的三種類型（超高頻考點）**：

| 問題類型 | 變數之間的關係 | 怎麼解 | 對應系統 |
|---|---|---|---|
| **結構性** Structured | **全部已知** | 直接告訴電腦關係 → 電腦求**最佳解** | **MIS** |
| **半結構性** Semi-structured | **部分已知**（不是「一半」） | **已知部分**：電腦**模擬**；**未知部分**：**決策者**下指示 → 結果回傳決策者 | **DSS** |
| **非結構性** Non-structured | **完全未知** | 電腦幫不上；決策者也不知道 → 回歸**數學模型／統計模型** | （人也難解） |

- ⭐ **MIS vs DSS 比較表**：

| 特性 | MIS | DSS |
|---|---|---|
| 功能重點 | **提供資訊** | **支援決策** |
| 系統設計策略 | 反應組織現況、**部門功能導向** | 反應前瞻性決策、**解決問題導向** |
| 問題類別 | **結構性**問題 | **半結構性**問題 |
| 系統輸出 | **綜合摘要報表** | **特殊決策分析報表** |
| 時程 | 過去到現在 | **過去到未來** |

#### (6) EIS 高階主管資訊系統（Executive Information System）

- **定義**：給**高階主管**使用，讓高階主管能**直接從電腦即時得到關鍵資訊**，不必透過中介使用者；輸出多為**彙整後的統計圖表或交叉分析表**。
- **為什麼不跟一般員工用同一套？** 因為高階主管要看的東西不一樣：他要**快速發現問題**、**及時做改善**。
- 你给高階主管看 TPS 幾千筆交易，他看不出問題；要整理成**長條圖／曲線圖**→ 從**高低起伏**一眼看出問題（**最低點＝問題所在**，例如某地區銷量最差 → 馬上訂行銷方案）。
- ⭐ **CSF 關鍵成功因素（3 點）**：
  1. 需**高階主管的支持與承諾**
  2. 需**高階主管擔任執行者**（要真的下去用）
  3. 需**與企業目標有關**

#### (7) 其他系統（配合題常考「縮寫 ↔ 中文 ↔ 定義」）

| 縮寫 | 中文 | 關鍵字 |
|---|---|---|
| **ES** | 專家系統 | 人工智慧的一支；把專家知識經驗建在電腦上，具**推論能力**，能**解釋推論結果**。四大部分：**知識庫、推論機件、知識獲得單位、交談式解釋介面** |
| **SIS** | 策略資訊系統 | 用資訊科技取得**競爭優勢**；強調**時間性**與**創造性** |
| **KMS** | 知識管理系統 | 管理組織學習與 Know-how，協助知識工作者**建立、重組、分享**知識 |
| **ERP** | 企業資源規劃 | 即時整合規劃分散各據點的資源。**狹義**：整合企業**內部**資源；**廣義**：含**上下游供應鏈**（內外部） |
| **整合型資訊系統** | — | 把性質相似的系統整合（如人事系統＋薪資系統） |
| **企業資訊系統** | — | 整合企業**所有**系統，同時含作業支援與管理支援 |

- ⭐ **DSS vs ES 比較**：

| 特性 | DSS | ES |
|---|---|---|
| 分析推論模式 | 資料庫模式、**數學模式** | **人工智慧邏輯推論**模式 |
| 設計策略目標 | **協助人**做決策 | **模擬專家並取代之** |
| 系統功能 | 分析預測 | 分析預測 **＋ 價值判斷** |
| 對話方式 | **人向機器**發問 | **機器向人**發問 |
| 資料庫內容 | **數值資料** | **法則、事實** |
| 知識運用 | 偏**計量**決策模型 | 專門**定性**知識 |

### 1-8 開發人員的角色（p.24 第 2 題考這裡）

| 角色 | 做什麼 | 考試重點 |
|---|---|---|
| **系統分析師** | **擷取使用者需求**；把需求轉換成資訊技術、企業處理與知識等元件並有組織結合起來 | 工作較難、要嚴謹；需求收錯→後面全錯 |
| **程式設計師** | 依分析設計藍圖寫程式、建資料庫、測試、安裝 | 把文件轉成電腦可執行指令 |
| **終端使用者** | 使用系統的人 | ⭐ **是「問題領域」的專家，但不是資訊科技專家**；扮演**提供使用者需求與企業知識**的角色。對自己的工作最熟，但不懂電腦，可能提出天馬行空的需求 |
| **企業經理** | 終端使用者的**高階主管** | 沒時間全程參與，但**承諾財力、人力、時間資源**、提出政策與限制 → **只參與前段** |
| **資訊系統經理** | 專案管理、**人員規劃（招募與訓練）**、軟硬體規劃、政策訂定 | 多系統同時開發時要**分配人力** |
| **DBA 與其他技術師** | 資料庫、網路、作業系統的建置管理維護 | 小公司常沒有，由資訊部門全包 |

### 1-9 ⭐ 建置策略（p.24 第 3 題考這裡，p.17 第二段）

**三大管道**
```
① 由公司內部獨立完成
   ├─ 使用者自建 EUC（End User Computing）
   ├─ 由資訊部門自行開發（最常見）
   └─ 由相關部門人員組成任務編組開發
② 由公司外部取得
   ├─ 委外開發 Outsourcing（要簽「建置合約」＋「維護合約」）
   ├─ 購買現成套裝軟體
   ├─ 引進同業系統
   └─ 租賃方式
③ 其他方式：上述綜合，或部分同業「聯合開發」共同找資訊公司（可分擔費用與風險）
```

**EUC 使用者自建**：使用者自己建系統。以前不可能（寫程式太難），現在工具人性化＋有 AI 協助，變成趨勢。
- **好處**：省掉與資訊部門**溝通協調的時間**（自己最懂自己要什麼，改也自己改）。
- 以前流程：開會→確認→寫程式→測試→上線，可能耗掉半年到一年。

**⭐ 選擇策略的 6 個考慮要素（背這張表就夠）**

| 要素 | 順序（最省/最快/最適 → 最差） |
|---|---|
| **成本** | 買套裝軟體**最低** ＜ 委外/ASP/聯合開發（居中）＜ **自行開發最高** |
| **時效** | 買套裝軟體**最快** ＞ 委外與 ASP（適中）＞ **自行開發最慢** |
| **適用性** | 買套裝軟體**最差** ＜ 委外與 ASP（居中）＜ **自行開發最佳** |
| **技術水準** | 本身沒技術能力 → 必須由**外部取得** |
| **人員調派** | 有沒有可用的人 |
| **經營策略** | 若系統是**競爭優勢**的核心 → 一定要**自己開發** |

### 2-2 八種模式逐一破解

#### ① 編碼與修正模式（1956 前，最早）

- **只有兩步**：寫程式（Coding）→ 修正（Debug）。
- **沒有方法論**（這是最大問題）。
- **缺點**：
  1. **沒有規劃與設計**，也沒使用者需求分析 → 改幾次後**程式碼邏輯難以理解**
  2. 沒有需求確認 → **不符合使用者需求**（自己想的，使用者不要）
- **沒有優點**（課本沒列）。

#### ② 階段模式（1956）

- **八個階段**（按步就班）：作業規劃 → 作業規格描述 → 程式規格描述 → **編碼** → 參數測試 → 整合測試 → 上線測試 → **系統評估**
- 已有**方法論雛型**：開發前要規劃、寫程式前要分析設計、上線前要測試。
- **四個問題**：
  1. 不論系統大小複雜度，**一律要跑八階段**（沒有彈性）
  2. 各階段**循序、沒有回饋（no recycle）**，發現前面做錯無法回頭改
  3. 每階段都要**考量完整系統範圍**，不能只看部分
  4. **假設需求可完整清楚描述**（前提假設太強）

#### ③ 瀑布模式（1970）⭐ 最常用

- **定義**：把開發過程分成「幾」個階段，每階段**清楚定義要做哪些工作、交付哪些文件**，各階段**循序執行且僅循環一次**。
- **有彈性**：
  - 小系統 → **3 階段**：分析 → 設計 → 實施
  - 大系統 → **擴充到 10 階段**：可行性分析、需求分析、系統分析、概念性設計、細部設計、程式編輯與單元測試、整合測試、安裝與系統測試、教育訓練、操作與維護
- **兩大加強（優點）**：
  1. **允許階段間回饋（recycle）**→ 盡早修正錯誤，**降低修改／重做成本**
  2. 每階段**明確定義工作與交付文件**→ 工作明確、容易掌握
- **又名 SDLC（系統發展生命週期）**。
- **執行上的缺失（5 點）**：
  1. 假設專案開始時需求可**完全清楚描述**
  2. 所有需求各階段都要同時考量，且**一個週期內完成**
  3. 程式編輯前**過於強調完整分析設計文件** → 需求一變文件要大改（⭐ 老師**不認同**這點：文件比 coding 重要）
  4. **週期長、使用者參與不足**（只在頭尾出現）
  5. 程式編輯在**後段才開始 → 風險較高**、失敗成本高（⭐ 老師也**不認同**：coding 本來就該在後段）
- ⭐ **p.69 第 1 題答案（為何普遍被接受，p.31）**：因為有**完整的規劃、分析、設計、測試與文件**等管理與控制，且階段有彈性、有回饋、每階段交付文件明確。

#### ④ 漸增模式（1972）

- **定義**：把**需求切成幾部分**，每個「部分需求」訂為一個**開發週期**，每個週期可**依序或平行**開發；每週期階段循序且僅循環一次。
- **前提**：必須**先完全掌握需求**才能切（由上而下把需求分成若干部分）。
- **與瀑布模式的不同**：
  1. 系統被切成**子系統/功能**，**可獨立依序開發**；瀑布是**各子系統須同時開發**
  2. 多個週期＝**多個版本**；每週期都有程式編輯與上線，**使用者每週期都參與** → **風險較低**
- **適用情況**：① 目標與需求可完整清楚描述　② **預算須分期編列**　③ 組織需要時間熟悉與接受新科技
- **缺點**：開發時間拉得很長。

#### ⑤ 雛型模式（1977）⭐ 最常用（另一個）

- **定義**：先針對使用者**需求較清楚**（或資訊人員較能掌握）的部分，快速依分析→設計→實施做出**雛型**；以雛型當作使用者與資訊人員**溝通與學習的工具**，透過操作與回饋**反覆修改擴充**，直到符合雙方約定。
- **為什麼需要它？** 瀑布要跑 1–2 年才有系統可用，而**需求又常常在變** → 使用者等不了。
- **流程四步驟**：需求擷取/分析（**雙方**）→ 雛型開發（**資訊人員**）→ 操作及檢討（**雙方**）→ 判斷「雛型與需求是否完全符合？」（**雙方**）→ 是：結束；否：回到需求擷取（**繞雛型週期**）。
  - 菱形＝**判斷條件**。
- **主要特性與原則（3 點）**：
  1. 強調雛型**盡早開發**及使用者**高度參與**
  2. 以雛型作為使用者與開發者的**需求溝通與學習機制**
  3. 從需求最清楚處著手，透過回饋反覆修改擴充，**每次反覆週期要盡可能縮短**
- **適用**：需求不明確、對領域知識（Domain Knowledge）不熟。**例子：遊戲軟體（每週更新新關卡/角色）、網站網頁（常更新消息活動）**。
- **潛在問題（2 點）**：
  1. **文件較不完備、程式較難維護**；短期滿足需求，**長期較易失敗**
  2. **缺乏整體規劃分析設計** → **不適用大型、多人參與**的系統
- **兩種策略（考配合題）**：

| 策略 | 說明 | 用途 |
|---|---|---|
| **演進式雛型**（最經典、最傳統的定義） | 從最清楚的需求快速跑完一週期做出**初版雛型**，用雛型與使用者溝通確認修改擴充，再進入下一週期…**逐步演進成最終系統** | 一般情況都用這個 |
| **用後丟棄式雛型** | 用**快而粗糙**的方式建雛型，只為讓使用者盡快決定需求、或讓資訊人員研發解法。**用過即丟**，故不考慮運作效率、可維護性、容錯 | **只用於風險最高處**（需求、知識概念、資訊科技整合最不清楚時）。因為丟棄＝**成本浪費**，公司實務上少用 |

#### ⑥ 螺旋模式（1986–1988，Boehm）

- **三個步驟形成一週期**（由內往外螺旋擴散）：
  1. **找出系統目標、可行實施方案與限制**
  2. **依目標與限制評估方案**（找出風險來源並設法解決：用雛型、模擬、標竿、參考點檢查、問卷、分析模式…）
  3. **由剩下的風險決定下一步驟**
- 週期反覆進行直到系統完成。
- **步驟三的判斷規則（重要）**：
  - 若**績效或使用者介面風險**強力影響程式開發 → 下一步用**演進式雛型**
  - 若雛型夠好用夠強韌 → 後續是一系列**雛型演進**
  - 若介面/績效風險都解決、程式與介面風險已掌控 → 走**瀑布模式**（可整合**漸增模式**）
- **特色**：**風險導向**；包容現有模式的大部分優點；某條件下會**等同於**瀑布/漸增/雛型模式。
- 圖形有 X 軸（回顧）與 Y 軸（成本），從圓心開始螺旋。

#### ⑦ 同步模式（1996）

- 源自製造業的**同步工程**，目的在**縮短開發時間**、加速版本更新。
- **三個主要構想**：
  1. **活動同步**：多個團隊**同時開發**（如 50 個功能切 5 塊，5 個團隊同時做）
  2. **資訊同步**：不同團隊資訊交流共享。三技巧：**向前傳遞**（把下一階段的重要問題與考量因素提前讓前一階段知道）、**向後傳遞**（把本階段結果傳給下一階段，最常用）、**建立資訊交換網路/群體工作支援環境**（像班群公告分享）
  3. **整合性的管理系統**：協調人員、資源、過程、產品的互動關係
- **執行程序**：功能組劃分 → 第 1~n 團隊同時開發 → **整合** → 測試 → 結束（→ 下一版本）
- **優點**：縮短開發時間，提高產品競爭力。
- **缺點**：步驟緊湊、**頻繁資訊溝通** → 專案管理複雜度大增、**人力成本提高**（5 團隊×5 人＝25 人）；沒有良好工具與管理方法就不易達標。
- **適用**：遊戲軟體、網頁製作。

#### ⑧ RUP 模式（1998，Jacobson 等）— 統一流程

- 結合**螺旋模式**概念，以**反覆與漸增**原理開發；**每次反覆都要產出可運作的系統版本**，且每週期都評估風險。
- ⭐ **兩個構面（一定要會分）**：

**動態構面 = 4 個階段（一週期，可反覆）**

| 階段 | 對應工作 | 一句話 |
|---|---|---|
| **初始** Inception | ＝需求分析 | 建立完整**系統需求與範圍**，降低企業風險 |
| **詳述** Elaboration | ＝系統分析＋系統設計（含coding與測試） | 處理**主要技術工作**，用可執行程式探討技術風險 |
| **建構** Construction | ＝做出可運作系統 | 建構**初步可運行系統**，演化內部版本確保可用性 |
| **轉移** Transition | ＝上線 | 移交使用者：備份、培訓、支援、維護 |

> 階段名稱不一樣，但**做的事跟需求分析→分析→設計→實作→上線一樣**。這是所有開發模式的通則：**換名字，不換內容**。

**新舊系統轉換方式（轉移階段要考慮，考配合題）**

| 方式 | 說明 | 風險 |
|---|---|---|
| **直接**用新系統 | 舊系統直接淘汰 | **最高**（新系統出問題就完了），但只需維護一套 |
| **前系統先轉移** | 先轉前置作業功能 | 中 |
| **分階段**轉移 | 把新系統切幾步轉 | 中 |
| **同步**（新舊並行） | 新舊系統同時用 | **最低**，但管理兩套很麻煩 |

**靜態構面 = 9 個核心工作流程（前 6 個是軟體工程，後 3 個是管理）**

| # | 工作 | 內容 |
|---|---|---|
| 1 | **企業塑模** | 現況問題分析→找替代方案→產生企業模型 |
| 2 | **需求** | 定義使用者需求與系統範圍 |
| 3 | **分析與設計** | 把需求轉成實作規格 |
| 4 | **實作** | Coding |
| 5 | **測試** | 發現與紀錄瑕疵 |
| 6 | **部署** | 安裝軟體、訓練使用者、移轉資料庫 |
| 7 | **組態管理與變更管理**（管理） | 追蹤維護專案演進的完整性 |
| 8 | **專案管理**（管理） | 提供專案架構、規劃、人員訓練、執行監督、風險管理 |
| 9 | **環境**（管理） | 流程與工具支援（選擇、裝配、配置工具） |

#### ⑨ 敏捷軟體開發（2001）＋ 四個成員

**四大開發理念（背這四句）**
1. **個體與互動** 勝於 流程與工具
2. **可運作的軟體** 勝於 全面性的文件
3. **與客戶的協同合作** 勝於 契約談判
4. **因應變化** 勝於 遵循計畫

**(a) DSDM 動態系統開發方法**
- 三部分：**專案前**（提專案建議、選被選專案）→ **專案生命週期**（核心）→ **專案後**（衡量專案/系統績效）
- 生命週期 **5 階段**：可行性研究 → 企業研究（＝需求分析）→ **反覆功能建模**（＝系統分析）→ **反覆設計與建置**（＝系統設計＋coding＋測試）→ 實施（上線）

**(b) Scrum 軟體開發**
- 兩階段：**衝刺準備**、**衝刺進行**
- **衝刺準備**：組成 Scrum 團隊（**產品負責人、Scrum 專家、開發團隊**）→ 需求擷取（客戶提出或訪談）→ **需求轉換**：把需求變成很多**故事（Story）**，故事集合＝**產品清單 Product Backlog**，並依重要性排**優先順序**
- **衝刺進行**：
  1. **衝刺規劃**：從產品清單挑這次要做的需求 → 每個故事細分為**工作項目** → 估算時間 → 標優先等級 → 分配給成員
  2. **衝刺執行**：為期 **1~4 週**，含設計、編碼、整合、測試
  3. **衝刺成果檢視**：開**衝刺檢視會議**，把成果展示給產品負責人
  4. **衝刺評估**：產品負責人開**自省會議**，檢討改善流程並提改善方案
  5. **反覆**：直到產品清單所有故事完成

**(c) 精實軟體開發（Lean）**
- 把**豐田生產系統（TPS）**的精實生產原則套到軟體開發。
- **七項原則**：消除浪費、增進學習、延遲決定、快速遞送、團隊授權、建置完整、**全盤檢視**。
- 較聚焦於 Toyota 一家公司，資訊較不公開。

**(d) 極限編程 XP（1996，Kent Beck）**
- **四項基本行為**：**編碼 Coding、測試 Testing、傾聽 Listening、設計 Design**
  - 傾聽＝收集使用者需求（實務上應是第一步）
  - 老師提醒：書上列的順序不等於執行順序（學生常先寫程式後補文件，但正確順序是**傾聽→設計→編碼→測試**）

#### ⑩ MDA 模式驅動架構（2001，OMG 定義）

- **最大差別**：每一個階段的**產出都是「模式（Model）」**，且該模式是**下一階段的輸入**；產出必須是**電腦可理解的正規模式（Formal Model）**。
- 流程與產出：
  1. 需求分析 → 產出**文字文件**
  2. 系統分析 → 產出 **PIM（平台獨立模式 Platform Independent Model）**
  3. 系統設計 → 產出 **PSM（特定平台模式 Platform Specific Model）**
  4. 程式編輯 → 產出**程式碼**
  5. 測試 → 上線

### 2-3 ⭐ 八種模式總比較（p.67–68 表 2-3，第 5 題答案來源）

| 模式 | 適用情況（什麼時候用） | 主要特性 |
|---|---|---|
| **編碼與修正** | 極小型、個人嘗試性程式 | 只有寫程式與修正，**無方法論** |
| **階段模式** | 需求明確的中小型系統 | 八階段、循序、**無回饋** |
| **瀑布模式** | 需求**明確且穩定**、大型有制度專案 | 階段有彈性(3~10)、**有回饋**、每階段交付文件、SDLC |
| **漸增模式** | 需求可完全掌握、**預算分期編列**、需時間熟悉新科技 | 需求切塊、多版本、**使用者每期參與**、風險較低 |
| **雛型模式** | 需求**不明確**、對領域知識不熟（遊戲、網站） | 使用者**高度參與**、反覆溝通、快速看到成果；文件較弱、不適合大型 |
| **螺旋模式** | **高風險**、大型複雜專案 | **風險導向**、三步骤循環、可整合雛型/瀑布/漸增 |
| **同步模式** | 需**縮短時程**、搶市場（遊戲、網頁） | 多團隊**活動同步**＋**資訊同步**、人力成本高、溝通複雜 |
| **RUP** | 中大型、需反覆與風險控制 | **動態 4 階段**＋**靜態 9 工作流程**、每回合產出可運作版本 |
| **敏捷/Scrum/XP/DSDM** | 需求變動快、要快速交付 | 個體互動、可運作軟體、客戶協作、因應變化 |
| **MDA** | 需模式化、可再利用、跨平台 | 每階段產出 **Model**（PIM→PSM），電腦可理解 |

> 第 5 題作答公式：**「該系統屬於＿＿（需求明確/不明確、風險高/低、時程急/不急）→ 我選＿＿模式 → 因為它＿＿（抄上表特性/適用情況）」**，原因合理即可，**沒有標準答案**。

## 3. 第三章：需求擷取與分析 ⭐ 本科重點章

### 3-1 為什麼需求分析最重要

- 需求分析是系統開發的**第一個步驟**，也是**最難、最花時間**的。
- 原因：**使用者需求常常在變**。這步做不好，後面全部無法進行。

### 3-2 ⭐ 需求分析階段的活動（三篇文獻 ＋ 作者的四項）

#### (1) Hooper & Hsia（1982）— **三件事**

| 工作 | 白話解釋 | 為什麼重要 |
|---|---|---|
| **需求判斷** | 判斷使用者提的需求**是不是真的、做不做得出來** | 使用者不懂 IT，會提天馬行空或技術上做不到的需求。**做不到要當場講**，否則最後做不出來，他會覺得你能力差。**這步最常被忽略** |
| **需求分析** | 針對「真正的需求」檢查有沒有**不一致、不完整、互相矛盾** | 把做不到的剔除後，檢視剩下的需求 |
| **需求溝通** | 用**最佳方式描述需求 → 轉成圖形** | 看圖比看文字一目了然，容易看出重點 |

#### (2) Grosz（1992）— **兩件事**（圖 3-1）

1. **需求擷取**：從系統範圍內各種事物與相關現象去了解、判斷、選擇，做成**描述性綱要**（＝一堆文字）
2. **需求轉換**：把描述性綱要（文字）用系統模式語法轉成**概念性綱要**（＝概念性圖形）

> **一句話**：需求分析真的就只做兩件事——**收集文字 → 轉成圖**。

#### (3) Byrd（1992）— **五件事**
1. 建立**組織資訊處理需求**
2. 發展**資訊系統目標**
3. 設計及**評估系統發展方案**
4. 整理分析師與上級、其他分析師、使用者**溝通的結果**
5. 從事**系統審核**

#### (4) 作者（吳仁和）自己提的**四項**（＝文件樣板的依據）

| # | 工作 | 對應文件樣板章節 |
|---|---|---|
| 1 | 瞭解**現有問題** | 一、問題描述 |
| 2 | 訂定**新系統目標** | 二、新系統目標 |
| 3 | 訂定**新系統限制**（成本、時程、軟硬體架構、安全、介面） | 三、新系統限制 |
| 4 | 定義**使用者巨觀需求** | 四、使用者需求（流程圖＋處理描述＋藍圖＋資料詞彙） |

### 3-3 ⭐⭐ 巨觀需求 vs 微觀需求（超高頻考點）

| | **巨觀需求 Macro** | **微觀需求 Micro** |
|---|---|---|
| **何時定出來** | **需求分析階段**就可以釐清確定 | **要到設計階段**才比較容易處理 |
| **內容** | 欲電腦化的**內外在環境**、**作業程序與範圍**、**輸出入所需資訊或表單**、**系統目標**、**限制**、**主要功能**、畫面包含哪些東西 | **使用者介面要求**、**例外狀況處理**、**錯誤／輔助訊息顯示**、**功能間先後順序**（A 做完才能做 B）、**錯誤檢查與警告訊息** |
| 特性 | 整體、廣泛 | 細微 |

> 記法：**「巨觀＝需求分析階段的產物；微觀＝設計階段的產物」**。需求分析只做巨觀。

### 3-4 ⭐⭐ 六種需求收集方式（p.110 第 1 題考這裡，任選兩種）

> 規則：**用哪一種沒有硬性規定**，可用**兩種以上混合**，能收集到需求就好。
> 訪談與開會討論**最常用**；查閱文件與觀察**建議當次要**。

#### ① 查閱文件
- 翻公司內部文件：**工作說明書、企業表單、手冊、操作手冊**。是了解企業運作邏輯的**初步工作**。
- **缺點：文件太舊**。系統改了多次但文件常沒更新 → 資訊**過時**。
- 老師順帶提醒：寫論文參考文獻抓**近五年**；只有引理論/定義/公式才可引很舊的。

#### ② 觀察
- **實地到使用者工作場所觀察**其行為。資料**正確性比查閱文件高**、能驗證與補充，是**第一手資料**。
- **缺點/瓶頸**：使用者多、每天狀況不同，不可能全看；**被觀察者行為會改變**（你一直去，他覺得你打擾）；最後只能挑少數人看 → **無法完整反映真實需求**。
- 技巧：**選擇「正常與例外情況」的時機或對象**來觀察。

#### ③ 訪談 ⭐ 最有效、最普遍
- 分析師與使用部門主管／相關人員**面對面**討論實際作業、報表與資訊需求。
- 可蒐集到**事實、選擇或推測**，並觀察**肢體語言、情緒、對現行系統的觀感**；有經驗者還能從回答中發現新問題。
- **兩種訪談**：

| | **開放式訪談** | **結構化訪談**（又稱標準化／導向式訪談） |
|---|---|---|
| 做法 | 事先**不預定表格、問卷或固定程序**，由使用者自由談論工作 | 問題**標準化**，過程**近似詢問而非交談**，要求深度與專業度較深 |
| 適用 | 分析師**對問題領域不熟**、或**無法預期**的情況 | 一般常用；所有受訪者回答**同一形式**的問題 |
| 步驟 | — | ① 分析師對主題做**簡短敘述**（問）② 使用者**深度回答**，分析師應在**深入適當程度時中止** ③ 有初步了解後進下一主題（一問一答） |

- ⭐ **問題的兩種性質（考配合題）**：

| | **開放性問題** | **封閉性問題** |
|---|---|---|
| 定義 | 可用來探索**無法預期**的回答或需明確詢問的問題 | 問題**可預期**、回答**可明確描述** |
| 優點 | 能讓**先前不知道的資訊浮現**、不斷探究新資訊 | **訪談時間較短**、問題可**較廣泛** |
| 缺點 | **花時間較長、較難作結論** | 所列**選項未必包含**受訪者要回答的答案 |

- **封閉性問題的三種設計形式**：
  1. **對與錯**（是非二選一）
  2. **多重選擇**（選擇題）
  3. **Likert 尺度**（衡量意見強弱：很好/好/普通/差/很差 = **5 點量表**；也有 **7 點量表**）
  - 主要還是以**問答題**為主，再搭配上述形式。
- ⭐ **進行訪談的 5 條準則（p.79，考「注意事項」就寫這 5 點）**：
  1. **仔細聆聽**並記錄重點；**取得同意**後可錄音/錄影，有效掌握內容
  2. 訪談結束後**48 小時（2 天）內**整理完，否則記憶會慢慢消失（最好回公司馬上做）
  3. 不論開放性或封閉性問題，**不要強調答案的對或錯**、不要講太多自己意見
  4. **不要對新系統做任何預期想法**、不預設答案（否則受訪者會隱藏真正想法）
  5. 從**潛在使用者、管理者、有經驗的專業人員**找各種觀點，才能設計出大多數人可接受的系統

#### ④ 問卷
- **適用**：潛在使用者**太多**或**分布太廣**（大型企業、公眾資訊系統），無法逐一親訪。
- 設計要有**經驗與練習**；題目是**靜態文字** → **語意與邏輯要清楚有條理**；多用**肯定句**。
- **同一問題可用不同問法** → 用來抓**無效問卷**（前後矛盾、全勾「無意見」＝亂填）。
- **先導測試（Pretest／前測）**：正式調查前先找約 30 人試填，目的在**修飾問卷**、及早發現問題、**提升效度**。
- ⭐ **抽樣方法（考配合題）**：

| 大類 | 方法 | 說明 |
|---|---|---|
| **機率抽樣** | **簡單隨機抽樣** | 名單逐一**編號**，用摸彩法或**亂數表**抽；每人被抽中機率相同（20 人抽 5 人＝1/4） |
| | **分層抽樣** | 先分成**若干互斥的組/層**，再從各層隨機抽預定數目（100 人分 5 組各 20，抽 20 人＝每組抽 4） |
| **非機率抽樣** | **便利抽樣** | 以**方便性**為主要考量（最容易找到、願意接受、動機高者）← 學生最常用 |
| | **判斷抽樣**（立意抽樣） | 依**設計者主觀判斷**選人，針對**符合某些特徵**者（如用系統 2 年以上、經常使用的人） |

#### ⑤ 開會討論
- 使用者代表與開發人員**齊聚一堂**，把知道的事實、觀念說出，互相溝通意見。
- **優點**：**較易獲得正確資料**；有不同觀念經眾人研究可修正；發揮**腦力激盪**效果。
- **缺點**：要**安排共同時間**，溝通協調較困難（老師認為提早通知即可克服）。

#### ⑥ JAD 聯合開發（Joint Application Development）
- **精神**：透過**2~5 天的集會**，讓開發者與顧客**快速、有效、深入**檢討需求並取得共識（常到外地/飯店，成本較高）。
- **具體結果**：產生**完整的需求文件**。
- ⭐ **五個步驟**：

| # | 步驟 | 內容 |
|---|---|---|
| 1 | **範圍界定** | 由**專案出資單位的高階主管**定義專案範圍並以文字記載，與 **JAD 召集人簽約** → 召集人取得授權。**高階主管只參與這一步** |
| 2 | **關鍵人員的熟悉** | 召集人花時間**訪談關鍵使用者與管理人員**，了解背景資料與重要需求 |
| 3 | **會議準備** | ① 整理**需求文件草稿** ② **分送**草稿 ③ 安排**助理人員** ④ 準備**會議室** |
| 4 | **會議進行** | 用**視覺輔助工具**（貼紙、白板、投影片、圖表、簡報檔）表達需求、達成共識 |
| 5 | **文件產生** | 會後**2~3 天**快速整理成需求文件，最後開**審查會議**確認內容 |

### 3-5 ⭐⭐ 需求表達工具（畫圖考題在這裡）

**為什麼要畫圖？** 3.2 收集到的是**一堆文字**，要轉成**圖形**才好溝通、好確認。
**工具四件套**：**流程圖（事件＋環境圖＋流程圖）→ 處理描述 → 藍圖 → 資料詞彙**。

```
使用者與企業需求（文字）
      │ 需求擷取
      ▼
   環境圖 ──► 流程圖（或活動圖）──► 藍圖（畫面）
                    │                    │
              處理描述（文字表）      資料詞彙（欄位表）
```

#### 3-5-1 ⭐ 流程圖符號（p.89 表 3-2，**必背**）

| 符號 | 課本名稱 | 白話＝ | 說明 |
|---|---|---|---|
| **長方形** | 作業處理 | **功能** | **動詞片語**（訂單處理、輸入成績、查詢成績） |
| **菱形** | 流程控制（決策） | **判斷條件** | 有「是／否」（符合／不符合）兩條線出去 |
| **開口矩形**（右側開口） | 資訊展示與儲存（報告） | **單據／表單** | 訂單、送貨單、生產需求、銷退單 |
| **線段＋箭頭** | 作業處理或資訊進行方向 | **資料流** | 有方向性 |
| **圓圈 A** | 接點 | **跨頁接續** | 第一頁底部畫 Ⓐ，第二頁頂端畫 Ⓐ |
| **右開口長形＋虛線** | 註解 | **註解** | 圖形上加說明，像程式註解 |

> 老師提醒：圖上的每個東西**都有意義**，不能隨便畫。虛線＝虛擬訊號（對照系統觀念圖的 feedback signal）。

#### 3-5-2 ⭐ 流程圖建立步驟（p.90，**照這四步就不會錯**）

1. **找出外部實體**：具有執行某些動作的個體 → 通常是**職稱**或**部門**（客戶、業務部、生產部、老師、學生）
2. **找出作業處理（功能）**：文字中的**動詞片語**（訂貨資料登錄、送貨處理、庫存檢查）
3. **檢視外部實體**：逐一檢討每個實體，找出**會主動引發刺激的主要實體**，從每個刺激找出其引發的一連串**高度相關處理**（這些處理合起來完成某功能）→ 形成一張流程圖
   - **關鍵規則**：「訂單處理後緊接著送貨處理，因此**兩者應在同一張流程圖**」
4. **繪製流程圖**：**實體放上方（加底線）**，其相關作業處理與資訊**分別畫在下方**
5. **檢視完整性**：所有流程圖是否涵蓋**整個系統範圍**

#### 3-5-3 處理描述（p.92 表 3-6）

- 對象：**流程圖上的每個長方形（處理/功能）都要有一份處理描述**。有幾個長方形就有幾份。
- **名稱必須與流程圖上的處理同名**（前後一致！老師特別糾正課本 p.101 表 3-8 的「訂單處理與庫存判斷」→ 建議刪掉「與庫存判斷」以跟圖一致）。
- 表格五欄：

| 欄位 | 寫什麼 |
|---|---|
| **處理名稱** | 與流程圖同名 |
| **執行程序與規則** | 這個功能怎麼執行（可**直接抄題目需求文字**，切成 1. 2. 兩點） |
| **資料輸入／來源** | 例如「訂單／客戶」 |
| **資料輸出／目的地** | 可能**兩條**（如「送貨訊息／業務部」＋「生產需求／生產部」） |
| **限制與備註** | 可寫可不寫 |

#### 3-5-4 藍圖（p.92 3.3.5）

- **藍圖＝畫面＝使用者介面**（老師說可以直接在「藍圖」後面括號寫「畫面」）。
- **有幾個功能（長方形）就要設計幾個畫面**。
- 這裡的畫面是**陽春版**：用繪圖軟體簡單畫文字方塊、標籤即可，**不用考慮程式語言的按鈕/標籤長相**（那是系統設計階段才做，會跟實際語言畫面一致）。
- 畫面上的 **A、B、C、D、E 只是欄位編號代號**（不是「顧客編號＝A」的意思），只為了對應下一張「資料詞彙」表。

#### 3-5-5 資料詞彙（p.93 3.3.6）

- 說明**藍圖上每個欄位**的細節。**一張藍圖對應一份資料詞彙**。
- 表格六欄：

| 欄位 | 說明 | 例子 |
|---|---|---|
| **編號** | 藍圖上的 A、B、C… | A |
| **欄位名稱** | 欄位中文名 | 客戶編號 |
| **長度／型態** | 幾個字、什麼型態（文字/數字/日期） | 4／Char |
| **鍵** | 是否為**主鍵 PK** | ✔ |
| **規則／格式／範圍／公式** | 有才寫（不是每格都要填） | 訂單編號＝年月日＋流水號；金額＝數量×單價 |
| **範例** | 實際長相 | W0000005 |

- 型態判斷技巧：
  - **電話**若含**連字號或括號**（區碼）→ 型態要定為**文字**；若純數字（07525200）→ 可定為**數字**
  - **日期**要寫清楚格式（**民國年還是西元年**、年月日順序）→ 使用者輸入才不會疑惑
  - **金額**有公式（數量×單價）→ 寫在「公式」欄

### 3-6 文件樣板（3.4 節，報告/專題第二章就用這個）

假設你的專題是做系統/網站/APP，**第一章是緒論（研究背景動機），第二章就是需求分析**，小節照這樣排：

```
2.1 問題描述          ← 現況有哪些問題（可用開會集思廣益、系統思考找問題）
2.2 新系統目標        ← 針對上述問題，新系統要完成什麼（目標必須跟問題「相關」）
2.3 新系統限制        ← 生產率、軟硬體架構、安全規定、系統介面、成本、時程、技術限制
2.4 使用者需求（巨觀） ← 四件套
    (一) 流程圖 1
         處理描述 1-1 … 1-n
         藍圖 1-1 … 1-m
         資料詞彙 1-1 … 1-m
    (二) 流程圖 2
         …
```

> 為什麼一定要寫「**系統範圍**」？口試時老師問「這個功能為什麼沒做」，你就翻到系統範圍那一節說明；多出來的需求可放到「**未來研究方向**」。

### 3-7 ⭐⭐ 夢幻公司個案（p.97 文字 → p.101 圖 3-4）

**個案背景**：夢幻公司成立 2005 年，從事**汽車機車零件買賣**，有自己的工廠製造部分零件。

**需求文字（第 1、2 點）**：
1. 業務部負責接訂貨單。接到客戶訂貨通知時需進行**訂貨資料登錄**，並做**庫存審核**；如庫存充足，則直接進行**送貨處理**；如庫存不足，則送**生產需求通知**給生產部，以便進行產品生產計畫。
2. 業務部也負責**送貨與送貨資料處理**（計算送貨總金額、遞送成品等），並傳送**送貨單**給客戶確認。
3. （第 3 點）業務部收到客戶**銷退單**通知，需記錄客戶編號、銷退成品數量、單價，並計算銷退金額…

**第 1 步：找外部實體（職稱/部門）**
→ **客戶**、**業務部**、**生產部**（用螢光筆在課本畫起來）

**第 2 步：找功能（動詞片語）**
→ **訂貨（訂單）資料登錄**、**送貨處理**、**庫存檢查**（判斷）

**第 3、4 步：畫成流程圖（答案 p.101 圖 3-4）**

```
  客戶            業務部                生產部
   │                │                     │
 [訂單] ────────► ┌──────────────┐
                  │ 訂單處理      │
                  └──────┬───────┘
                         ▼
                  ◇ 成品庫存是否足夠？
                    │是           │否
                    ▼             └──► [生產需求] ──► 生產部
              ┌──────────────┐
              │ 送貨處理      │
              └──────┬───────┘
                     ▼
                 [送貨單] ────────────────► 客戶
```

**常見扣分點（老師特別叮嚀）**
1. **每個功能都要有進有出（IPO）**：送貨處理不能只有輸入 → 一定要補輸出「**送貨單 → 客戶**」。
2. 外部實體要畫在**最上方並加底線**。
3. **一點需求對一張圖**；**前後連續動作才合併成一張**（第 1、2 點是連續動作 → 同一張）。
4. 圖的內容**不必跟課本一字不差**：「訂單處理」或「訂貨資料登錄」都可以；菱形寫「是否有庫存」或「成品庫存是否足夠」都可以，**意思到就好**。
5. 判斷條件一定是**菱形**，且要有**兩條**出線。

**課本漏掉、要自己補的兩處**

  - 處理名稱：**送貨處理**

### 一句話殺手（問答題開頭這樣寫）
- **TPS**：把公司日常例行性的大量交易處理自動化，並保存交易記錄、產生表單。
- **MIS**：人機整合系統，提供資訊以支援組織日常作業、管理與決策（Davis, 1968）。
- **DSS**：以試誤法、交談方式協助解決**半結構性**問題，強調「支援」。
- **EIS**：讓高階主管不經中介、即時取得關鍵資訊，輸出統計圖表/交叉分析表。
- **ES**：把專家知識建在電腦上並具推論能力，能解釋推論結果。
- **結構性問題**：變數與其關係**全已知**→電腦求最佳解（MIS）。
- **半結構性**：部分已知→已知部分電腦模擬、未知部分決策者下指示（DSS）。
- **非結構性**：全未知→回歸數學/統計模型。
- **瀑布模式**：階段循序、僅循環一次、有回饋、每階段交付文件，又稱 SDLC。
- **雛型模式**：先做需求最清楚的部分快速產出雛型，作為溝通學習工具，反覆修改至符合約定。
- **巨觀需求**：需求分析階段定出（環境、範圍、輸出入、目標、限制、主要功能）。
- **微觀需求**：設計階段才定出（介面、例外處理、錯誤訊息）。

### 畫圖 SOP（畫圖題照抄這 6 步）
1. 讀文字，**圈出職稱/部門** = 外部實體
2. **圈出動詞** = 功能（長方形）
3. 找出**判斷句**（如果/是否）= 菱形（兩條出線）
4. 找出**單據名稱** = 開口矩形
5. 外部實體排最上面**加底線**，動作往下畫，箭頭標方向
6. **檢查每個功能都有輸入也有輸出**（IPO 不漏）、檢查連續動作是否該合併同一張圖
